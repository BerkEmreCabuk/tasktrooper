# Mockery v3 & Suite Tests (Go)

## Overview

Go tests here follow three non-negotiables: mocks are **generated by Mockery v3** (never hand-written), multi-case tests are **table-driven**, and grouped tests use a **testify suite**. Hand-rolled mocks drift from the interface, table tests keep cases honest, and suites share setup without copy-paste.

**Core principle:** You never hand-write a mock. If you typed `type mockFoo struct` in a test, delete it and generate it with Mockery v3.

## Mockery v3 — generate, don't hand-write

- Mocks come from the port interfaces in `internal/port`, generated by Mockery v3. Configure once in `.mockery.yaml`; regenerate with `mockery` when an interface changes.
- **Never** hand-write a mock struct, and **never** add test-only methods to a production type to make it mockable — depend on the port interface instead.
- v3 generates an `expecter` API — use the typed `EXPECT()` methods, not raw `On("MethodName", ...)` string calls, so a renamed method breaks compilation instead of silently passing.

```go
repo := mocks.NewTaskRepository(t)            // generated constructor, auto-asserts on cleanup
repo.EXPECT().Create(mock.Anything, task).Return(nil).Once()
svc := NewTaskService(repo)
```

If the interface changes and you forgot to regenerate, the test won't compile — that is the point.

## Table-driven tests

Every function with more than one case is a table. One row = one behavior with a descriptive name.

```go
func (s *TaskServiceSuite) TestCreate() {
    tests := []struct {
        name    string
        title   string
        setup   func(*mocks.TaskRepository)
        wantErr error
    }{
        {name: "valid title persists",
            title: "Report",
            setup: func(r *mocks.TaskRepository) { r.EXPECT().Create(mock.Anything, mock.Anything).Return(nil).Once() }},
        {name: "blank title rejected before DB",
            title: "  ",
            setup: func(r *mocks.TaskRepository) { /* no EXPECT: repo must NOT be called */ },
            wantErr: domain.ErrInvalidTitle},
    }
    for _, tt := range tests {
        s.Run(tt.name, func() {
            repo := mocks.NewTaskRepository(s.T())
            tt.setup(repo)
            _, err := NewTaskService(repo).Create(s.ctx, tt.title)
            s.ErrorIs(err, tt.wantErr)
        })
    }
}
```

Cover success, every error path, and edges (empty, not-found, conflict) as rows. A blank-title row that sets NO expectation proves the repo is never touched on invalid input.

## Testify suite

Group a type's tests in a `suite.Suite` for shared setup (context, fixtures) via `SetupTest`. Keep per-row mocks fresh inside `s.Run` so rows don't leak expectations into each other.

```go
type TaskServiceSuite struct {
    suite.Suite
    ctx context.Context
}
func (s *TaskServiceSuite) SetupTest() { s.ctx = context.Background() }
func TestTaskServiceSuite(t *testing.T) { suite.Run(t, new(TaskServiceSuite)) }
```

## Rules

- Mock ONLY at port boundaries (repositories, external clients). Domain logic uses real domain values — no mocks.
- Assert on behavior and returned values, not on internal call ordering — over-specified expectations break on every refactor. Use `.Once()`/`.Times(n)` only where the count is the behavior under test.
- Keep the suite green and output pristine: a happy-path test that logs errors hides real failures.

## Common Mistakes

- A hand-written `mockFoo` in the test file → generate with Mockery v3.
- Raw `.On("Create", ...)` string calls → use `.EXPECT().Create(...)`.
- One giant test with `if`-branches per case → make it a table.
- Copy-pasted setup across test funcs → move it into a suite `SetupTest`.
- Mocking a domain value object → construct the real one.

## Red Flags

- `type mock... struct` appears anywhere under a test.
- A test still compiles after an interface method was renamed → you're using string-based `On`, not the v3 expecter.
- Rows share a mock instance and pass only in a specific order.
